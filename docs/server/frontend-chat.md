# Chat integration with the new frontend

Branch: `feature/rafael-sapalo/frontend-backend-integration`, based on
`cleanup/frontend-dev-pr`. The new chat page, arrow send button, bubbles,
composer, history sheet, themes, crisis support and navigation retain their
design. The deletion confirmation now describes account-wide deletion.

## Messaging and sessions

- Native WebSocket: `/chat/ws`, authenticated by the Authorization header.
  Credentials never enter the URL. Before connecting, chat uses the shared
  HTTP client to validate the account and refresh expired credentials. The
  server validates the session again before accepting each message; logout or
  account deletion invalidates an already-open connection.
- Send JSON `{message, conversationId, requestId, messageId}`. All new client
  request/message IDs are UUIDs. Message text is trimmed and bounded to 16,000
  characters; conversation IDs are bounded to 200 characters.
- `messageId` identifies the stable user message; `requestId` identifies one
  attempt. A retry retains the message ID and uses a fresh attempt ID.
  Retrying cannot change another user's message or silently replace its text.
- Kafka keys are generated by the server. The existing AI bridge returns
  `userId`, `conversationId`, `requestId`, `sourceMessageId`, `sourceHash`
  and `response` on `elyrii.ai.responses`.
- The consumer checks source ownership, conversation, content hash and context
  suppression, then commits the reply before sending a correlated
  `{type: "reply", requestId, conversationId, message, messageId, createdAt}`.
  Errors have the same correlation fields. A response goes only to the
  originating socket; closing one socket cannot remove another's requests.
- Each source can have one persisted reply. Duplicate Kafka results and retries
  return that canonical reply. Database errors leave the Kafka result
  uncommitted for replay. A 45-second delivery deadline releases a stalled
  attempt; a late result remains recoverable through history/retry and is never
  broadcast into a replacement conversation.
- Missing replies remain retryable after restoring history. A server-confirmed
  reply is distinct from an unsent local message.

## History and deletion

- `GET /chat/conversations?limit=50` returns account-owned conversation metadata.
  Follow the last row with paired `beforeDate` and `beforeId` parameters.
  Timestamps are serialized in UTC with millisecond precision.
- `GET /chat/history?conversationId=...&limit=50` returns a bounded chronological
  page. Use the oldest returned message's `id` as `beforeId` for older messages.
  Calls without a conversation preserve the existing account history API.
- SQLite keeps encrypted account-owned titles/messages. Remote pages are merged
  by stable IDs and read in timestamp/ID order. Local-only histories retain
  their insertion order and are never silently uploaded.
- History refresh reconciles known server pages, removing remotely deleted
  conversations while retaining unvisited pages and unsent local conversations.
  Network/server outages may use the local copy; 401 and invalid ownership
  responses never fall back to another account's data.
- `DELETE /chat/conversations/:id` uses the existing context lifecycle deletion.
  It deletes the owned source messages and their dependent replies/context
  records. A minimal conversation tombstone prevents queued sends or retries
  from recreating a deleted conversation. Account deletion removes tombstones
  through the user foreign key.
- A startup routing race was fixed: once a returning account's completed setup
  flag loads, it leaves onboarding and reaches the authenticated application.

## Migration and configuration

Apply `0008_chat_mobile_contracts.sql` through the normal ordered
`bun run db:migrate` workflow. It adds the nullable reply source, unique reply
index, composite source foreign key, cursor index and deletion tombstones.
Existing messages remain intact. Deploy the current AI bridge with source
provenance fields and provision its Kafka topics before enabling consumers.
The existing context/outbox/summary/suppression services remain in place.

No shared or production migration, deployment or push is performed by this work.

## Local verification

```sh
cd elyrii_server
POSTGRES_BINDIR=/opt/homebrew/opt/postgresql@17/bin bun run test:chat
```

The runner starts its own PostgreSQL and Kafka instances on loopback, a real
API/WebSocket server and a deterministic test AI worker, then stops them.
The worker exercises real Kafka transport without downloading a model or
calling an external AI provider. This does not evaluate generated advice.

It applies the real baseline and context/outbox/summary/suppression migrations,
omitting vector-only DDL and the embedding migration from the fixture. The
pgvector migration/embedding suite remains `scripts/test-context-db.sh`; this
fixture is not a deployment migration recipe.

Add a dedicated already-booted simulator to exercise the actual new screens:

```sh
POSTGRES_BINDIR=/opt/homebrew/opt/postgresql@17/bin \
IOS_SIMULATOR_UDID=<dedicated-udid> \
HOLD_CHAT_QA_FRAME=true \
bun run test:chat
```

The native test sends messages with the existing arrow button, switches between
two conversations, rebuilds app state while retaining Keychain/SQLite, restores
a conversation, and deletes it through the existing confirmation. The optional
hold leaves the restored chat visible for simulator-browser inspection.
This is an app bootstrap test, not a force-kill/relaunch or physical-device test.
